# Release process

Tags matching `v*` trigger [`.github/workflows/release.yml`](../.github/workflows/release.yml).

## What a release contains

Asset names use the tag verbatim, including the leading `v` (tag `v0.4.0`
produces `oxide-flux-v0.4.0-…`).

| File | Platform | Contents |
| --- | --- | --- |
| `oxide-flux-<tag>-windows-x86_64-setup.exe` | Windows, per-user installer | NSIS installer built from [`installer/oxide-flux.nsi`](../installer/oxide-flux.nsi); installs `oxide-flux.exe`, `fluxd.exe`, README, LICENSE, THIRD_PARTY |
| `oxide-flux-<tag>-windows-x86_64.zip` | Windows, portable | the same five files, no installer |
| `oxide-flux-<tag>-linux-x86_64.tar.gz` | Linux | `oxide-flux`, `fluxd`, README, LICENSE, THIRD_PARTY |
| `oxide-flux-<tag>.spdx.json` | any | SPDX 2.3 JSON SBOM of the repository, generated by [`anchore/sbom-action@v0`](https://github.com/anchore/sbom-action) (syft) |
| `SHA256SUMS` | any | SHA-256 of every asset above, including the SBOM and the installer |
| `oxide-flux-checksums.cosign.bundle` | any | keyless cosign signature of `SHA256SUMS` |

`SHA256SUMS` is generated in `dist/` after the SBOM is written and before
`gh release create dist/*`, so it covers every uploaded file. The cosign bundle
is created after the checksums, which is why it is not listed in them.

The GitHub-generated source archives for the tag are the GPL corresponding
source; do not delete releases.

## Windows installer (per-user NSIS)

The installer is compiled on the Windows runner in the `build` job, between
packaging the zip and uploading `dist/*`:

```pwsh
makensis /DVERSION=0.4.0 /DFILEVERSION=0.4.0.0 `
         /DSTAGEDIR=<repo>\stage /DLICENSEFILE=<repo>\LICENSE `
         /DOUTFILE=<repo>\dist\oxide-flux-v0.4.0-windows-x86_64-setup.exe `
         installer/oxide-flux.nsi
```

`<repo>\stage` holds the five files listed above and `dist\` must exist; CI
creates both, and a local build can reuse the same layout after
`cargo build --release --bin oxide-flux --bin fluxd`.

What it does:

- **Per-user only.** `RequestExecutionLevel user`, default directory
  `%LOCALAPPDATA%\Programs\OxideFlux`, Start Menu folder in the current user's
  profile, optional desktop shortcut (unchecked by default), and an
  Add/Remove Programs entry under
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\OxideFlux`
  (DisplayName "Oxide Flux", publisher, version, icon, `EstimatedSize`,
  `QuietUninstallString`). No elevation, no machine-wide state.
- **Running instances are never killed.** Before copying or deleting files the
  installer probes the installed `oxide-flux.exe` and `fluxd.exe` with a
  write-mode open (a running image cannot be opened for writing) and shows a
  Retry/Cancel message telling the user to close the app or stop the daemon.
  Silent runs (`/S`) cancel instead of guessing.
- **File associations belong to the app.** Setup never writes
  `HKCU\Software\Classes`; the app registers `.torrent` and `magnet:` on first
  launch (or with `--register`). The uninstaller runs
  `"$INSTDIR\oxide-flux.exe" --unregister` first, which removes only entries
  that point at this installation, then removes the shortcuts, the files it
  shipped, `$INSTDIR` (plain `RMDir`, so user files are never wiped) and its
  registry keys. Other clients' associations and Windows `UserChoice` are
  untouched.
- **User data is kept.** `%APPDATA%\OxideFlux` (session state, settings,
  single-instance lock) survives an uninstall.
- **No icon yet.** The repository ships no `.ico`; add `MUI_ICON`/`MUI_UNICON`
  to the script once one exists. `signtool` signing of the produced setup `.exe`
  is what makes SmartScreen show the publisher name.

Uninstall silently with `"%LOCALAPPDATA%\Programs\OxideFlux\uninstall.exe" /S`,
or override the install root on the command line with `/D=...` (last argument,
unquoted by NSIS convention).

### Why NSIS per-user, not MSI or MSIX

- **NSIS per-user now.** The app is a single-user desktop program: state in
  `%APPDATA%`, associations in `HKCU`, no service or driver. A per-user `.exe`
  installs without UAC, cannot break another user's profile, and keeps the
  `.torrent`/`magnet:` registration in the same user context the app writes to.
- **MSI (WiX) later, for enterprise.** Managed deployment wants per-machine
  install, GPO/Intune push, repair, patching, transform files and an
  administrative install point. Those requirements do not exist for a
  single-user preview build, and an MSI would force elevation that the app
  itself never needs.
- **MSIX not yet.** Package identity virtualises `%APPDATA%`/`%LOCALAPPDATA%`
  and the registry, which collides with the app's state paths and its
  `HKCU\Software\Classes` writes; packaged Win32 apps cannot freely take over
  file associations; mpv is hosted in a child Win32 window created from the app,
  which is fragile under packaged-app interop; and MSIX signing needs a
  certificate/profile the project does not have. Revisit after auto-update and
  an installer MSIX identity are designed together.

## Verify a download

```sh
sha256sum -c SHA256SUMS
cosign verify-blob SHA256SUMS \
  --bundle oxide-flux-checksums.cosign.bundle \
  --certificate-identity-regexp "https://github.com/edhases/oxide-flux/.github/workflows/release.yml@refs/tags/.*" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

## Windows code signing (Authenticode)

### The 2023 rule change: a PFX secret is not the future

Since **1 June 2023** the CA/Browser Forum Code Signing Baseline Requirements
require the private key of a publicly trusted **OV or EV code-signing
certificate** to be generated in and used from a FIPS 140-2 Level 2 (or Common
Criteria EAL4+) hardware module. CAs now issue those keys as non-exportable
keys inside a token, an HSM, or a cloud signing service. There is no `.pfx` to
download, so `WINDOWS_PFX_BASE64` + `WINDOWS_PFX_PASSWORD` **cannot hold a
newly issued public certificate**. The workflow keeps that block as a fallback
for certificates whose keys are still exportable (issued before the rule
change, private/internal CAs, or a self-signed test cert) — it is not a path to
a trusted build.

Without Authenticode the release is still verifiable: cosign keyless signing of
`SHA256SUMS` binds every asset (installer included) to this repository's
`release.yml` workflow via the GitHub OIDC identity, and that signature is
checked against the public Rekor log. What is missing is Windows' own
publisher display and SmartScreen reputation, which stays poor until enough
downloads accumulate for that exact signing identity.

### Options for this project

| Option | Cost | How signing happens in CI | Notes |
| --- | --- | --- | --- |
| **[SignPath Foundation](https://signpath.org/)** | free for OSS | Installer/zip uploaded as a workflow artifact, then `signpath/github-action-submit-signing-request@v1` submits a signing request; SignPath signs with its own HSM-held certificate and returns the signed files | Built for open source (OSI-approved license, public repo, application approved by SignPath). No certificate to buy or renew. Best fit here. |
| **[Azure Trusted Signing](https://learn.microsoft.com/azure/trusted-signing/)** (now documented as "Artifact Signing") | about US$10/month | [`Azure/trusted-signing-action`](https://github.com/Azure/trusted-signing-action) (published today as `Azure/artifact-signing-action`) signs files through a Signing account + certificate profile; authenticate with OIDC (`azure/login`) or a service principal | Needs an Azure subscription and a completed identity validation (organization with verifiable history, or an individual in a supported country). Keys never leave Microsoft's HSM. |
| **CA-issued OV/EV + cloud HSM** — DigiCert [KeyLocker](https://www.digicert.com/signing/code-signing-certificates), [SSL.com eSigner](https://www.ssl.com/esigner/), [Certum](https://www.certum.eu/en/code-signing-certificates/) | hundreds of US$/year | Their agent/CLI (`smctl`, eSigner CKA, SimplySign) runs in the job and signs with a key that stays in the CA's cloud HSM; CI holds only an API credential | Most control and the strongest identity (EV historically earns SmartScreen trust fastest), but the most setup: purchase, identity documents, per-signing auth. |
| Legacy `*.pfx` (current fallback) | — | `signtool /f signing.pfx` as in the workflow | Only possible with an exportable key. Keep for internal/self-signed builds. |

Prices and eligibility change; verify on the vendor pages. The practical plan:

1. Apply to **SignPath Foundation** — the practical zero-cost route to a
   publicly trusted Authenticode signature for an OSS project.
2. If a legal entity with a supported country becomes available, add
   **Azure Trusted Signing** for a cheap per-month certificate the project
   controls.
3. Buy an OV/EV certificate with cloud HSM only if a specific distributor or
   enterprise requires the project's own name in the signature.

### SignPath wiring (recommended, not yet enabled)

The application answers are prepared in
[`signpath-application.md`](signpath-application.md); approving it is the only
step that needs a human.

SignPath signs an **artifact** of the workflow, so the job uploads the files to
sign, submits the request, and downloads the signed output:

```yaml
permissions:
  contents: read
  id-token: write

jobs:
  sign:
    runs-on: windows-latest
    steps:
      - uses: actions/upload-artifact@v4
        id: unsigned
        with:
          name: windows-unsigned
          path: |
            dist/oxide-flux-*-windows-x86_64-setup.exe
            stage/oxide-flux.exe
            stage/fluxd.exe

      - uses: signpath/github-action-submit-signing-request@v1
        with:
          api-token: ${{ secrets.SIGNPATH_API_TOKEN }}
          organization-id: ${{ secrets.SIGNPATH_ORGANIZATION_ID }}
          project-slug: oxide-flux
          signing-policy-slug: release-signing
          artifact-configuration-slug: oxide-flux-windows
          github-artifact-id: ${{ steps.unsigned.outputs.artifact-id }}
          wait-for-completion: true
          output-artifact-directory: signed
```

Repository secrets: `SIGNPATH_API_TOKEN` (project-scoped API token),
`SIGNPATH_ORGANIZATION_ID`. The remaining values (`project-slug`,
`signing-policy-slug`, `artifact-configuration-slug`) are chosen in the SignPath
UI and are not secrets. SignPath's artifact configuration decides which files
inside the uploaded artifact get signed and how they are packaged back.

### Azure Trusted Signing wiring (alternative)

```yaml
permissions:
  contents: read
  id-token: write

jobs:
  sign:
    runs-on: windows-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - uses: Azure/trusted-signing-action@v0
        with:
          endpoint: ${{ secrets.TRUSTED_SIGNING_ENDPOINT }}   # https://<region>.codesigning.azure.net
          signing-account-name: ${{ secrets.TRUSTED_SIGNING_ACCOUNT }}
          certificate-profile-name: oxide-flux
          files: |
            dist/oxide-flux-*-windows-x86_64-setup.exe
            stage/oxide-flux.exe
            stage/fluxd.exe
```

`azure/login` with OIDC needs a federated credential on an Entra app
registration (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` as
repository secrets/variables). `TRUSTED_SIGNING_ENDPOINT` and
`TRUSTED_SIGNING_ACCOUNT` identify the Trusted Signing account.

### What the workflow does today

1. `Sign Windows binaries (Authenticode, optional)` — signs `oxide-flux.exe` and
   `fluxd.exe` before the zip is built, only when the PFX secrets exist. This
   must stay before `makensis`: the installer embeds those binaries, so signing
   them afterwards would leave the files inside `setup.exe` unsigned.
2. `Build Windows installer (NSIS, per-user)` — compiles the setup `.exe` from
   the already-signed binaries in `stage/`.
3. `Sign installer (Authenticode, optional)` — signs the setup `.exe` itself,
   with the same optional PFX. It runs last because Authenticode signs final
   bytes: any later change to that file would drop the signature.

Both signing steps are no-ops when the secrets are absent, so a fork or a
secret-less push still produces a complete release. Moving to SignPath or Azure
means replacing these two blocks with the provider's action, keeping the same
ordering (binaries first, installer last).

## Not automated yet

- macOS builds and notarization (no runner configured; iced supports macOS, the
  app has not been validated there).
- Auto-update (decide the channel and signature model before 1.0).
- MSI/WiX for managed deployment, and ARM64 Windows builds.
- A `cargo deny check licenses` / `cargo cyclonedx` gate (the SBOM is
  repository-level; a Cargo-native SBOM would list resolved crates only).
